# 麦当劳中国 MCP 使用规则

本技能对应 DeepSeek Harness 中的 MCP 服务 `mcd-mcp`
（`https://mcp.mcd.cn`，Streamable HTTP）。工具不是本 bundle 硬编码的：
`@deepseek-ai/dsh-mcp-client` 在启动、重连和服务端发出工具列表变更通知时
调用 `tools/list`，自动注册服务端当前暴露的全部工具（目前约 33 个，数量会
变化）。

## 前置检查

开始前先确认当前会话确实有 `mcp__mcd-mcp__*` 工具：

- **没有这些工具时，不要编造工具名、不要假装调用成功，也不要用通用 HTTP
  请求绕过 Harness 的 MCP 客户端。** 直接告诉用户 MCP 尚未连接，并给出排查步骤：
  1. 让用户在 Harness 的 **Plugins → mcd-mcp** 配置里填写 `MCD_MCP_TOKEN`
     （token 从 https://open.mcd.cn/mcp 控制台获取）；也可以使用 Harness 启动
     环境中的同名变量。不要在聊天里向用户索要 token。
  2. 查看 `mcd-mcp` 行：两个来源都没有 token 时该行会被有意禁用；token 无效时
     连接会失败并记录错误。
  3. 保存/更新 token 后重启 Harness（或重新挂载该 bundle），再发起新会话。
  4. 仍然失败时，让用户检查网络/代理和 token 是否过期；不要用猜测的 token 重试。
- 工具存在但缺少某个操作时，说明服务端当前没有暴露它（工具列表会变化）；
  如实告知，不要臆造替代名称。

## 何时使用

用户提到麦当劳、麦乐送、McDonald's，或要求：

- 查附近门店、营业时间、菜单、单品/套餐
- 算价、比较优惠、查可用券、领券/绑券
- 下单、查订单、取消/售后

不用于其他品牌，也不要把本技能当成通用外卖接口。

## 工具发现与命名

- **不要**在回答、代码或计划里写死工具清单、数量或参数 schema。每次以当前会话
  实际注册的工具为准。
- Harness 把工具注册为 `mcp__<serverName>__<rawName>`，本服务即
  `mcp__mcd-mcp__<tool>`；原始名里的 `-` 会保留，例如 `create-order` →
  `mcp__mcd-mcp__create_order`、`calculate-price` →
  `mcp__mcd-mcp__calculate_price`。超过 64 字符或含非法字符时，bridge 会追加
  一段短哈希以保证唯一；**始终以实际注册名为准**。
- 如果需要的工具不存在或返回 “unknown tool”：按“前置检查”处理，不要臆造。
- 只读操作可以连续调用；写操作按下面的确认流程执行。

## 写操作：先确认，再执行

以下操作会花钱或改变账户/订单状态，**调用前必须让用户明确确认**：

- `create-order`（创建订单/下单）
- `auto-bind-coupons`（自动绑券/用券）
- 其他语义为 create / submit / pay / order / cancel / refund / update / delete /
  bind / claim / redeem 的工具

确认流程：

1. 先用只读工具取全信息，把下列内容列给用户：
   - 门店（名称、地址/取餐方式）
   - 商品与数量
   - 单价、总价，**每项都标单位**（元或分）
   - 优惠券、抵扣金额、配送费/打包费
   - 预计取餐/送达时间
2. 明确询问“是否确认下单/绑券？”，等待用户明确回复（如“确认”“是”“下单”）。
   - “随便”“你决定”“应该可以”“先看看”**不算确认**。
   - 用户沉默、转移话题或要求修改时，不执行。
3. 用户修改任一信息（商品、数量、门店、券）后，重新算价并再次确认。
4. 一次确认只对一次写操作有效；不得一次确认后连续下单或批量绑券。
5. 写操作失败或超时：先查询订单/券状态，确认没有生效后再决定是否重试，避免
   重复下单。
6. 不要为了“拿价格”或“看看能不能用”而调用写工具；算价用只读的
   `calculate-price`。
7. 即使 Harness 当前权限预设会弹出额外审批，也仍要先完成上面的用户确认。

确认话术示例：

```text
即将下单（写操作）：
- 门店：<名称 / 地址 / 取餐方式>
- 商品：<名称 × 数量，单价 ¥x.xx>
- 合计：¥xx.xx（xxxx 分，已核对单位）
- 优惠券：<券名，抵扣 ¥x.xx>
- 预计取餐：<时间>
确认下单请回复“确认”；回复其他内容将取消。
```

## 金额单位：分 vs 元

- `calculate-price` 的金额**可能是分（fen / cents）**；其他工具（菜单、订单、
  优惠券）**可能是元（yuan）**。不要假设整个会话单位一致。
- 判断依据（按优先级）：
  1. 字段名：含 `fen`、`cents`、`amount_fen`、`price_fen`、`total_fen` 的按分处理；
  2. 工具描述 / JSON Schema / 返回值中的单位说明；
  3. 数值形态：总是整数且明显偏大（如 1250 表示 12.50 元）通常暗示分，但这只是
     线索，不是证据；
  4. 同一响应内字段之间的一致性（单价 × 数量是否等于总价）。
- 拿不准时：保留原始数值，标注“单位未确认”，并向用户说明；**不要静默除以 100**。
- 展示时始终带单位，并在需要时给出换算：`¥12.50（1250 分）`。换算只用于展示，
  计算用原始值，避免反复四舍五入。
- 优惠券抵扣、配送费、打包费分别标单位后再汇总；不要把分和元直接相加。
- 如果用户只接受元，先确认单位再换算；换算公式：1 元 = 100 分。

## 限流与 429 退避

- 服务端限流约 **600 次/分钟**。批量查门店/菜单时合并请求、去重、串行执行，
  避免并发轰炸。
- 收到 HTTP 429 或错误体提示 rate limit：
  - 优先遵守响应里的 `Retry-After`；
  - 没有该头时指数退避：1s、2s、4s、8s、16s，叠加 0–500ms 随机抖动，最多 5 次；
  - 退避期间暂停其他请求，不要“换一个工具继续打”；
  - 仍失败就停止，告知用户“触发限流，请稍后再试”，不要无限重试。
- 写操作遇到 429：不要盲目重试。先查询订单/券状态确认请求是否已被处理，再决定。
- 网络超时/5xx 同样适用退避；401/403 **不要重试**，直接提示 token 失效/权限问题。

## 认证与隐私

- Token 从 https://open.mcd.cn/mcp 控制台获取。优先在 Harness 的 Plugins 设置里
  填写（volatile secret，UI 脱敏，保存在本机 profile，不写入本仓库）；也可以
  使用启动环境中的 `MCD_MCP_TOKEN`。`cordis.patch.yml` 只通过 `!!js` 在挂载时
  拼出 `Authorization: Bearer ...`。
- 不要读取、回显、截取或记录 token 的任何部分；不要在回答、文件、命令参数或
  日志中输出它。
- 用户索要 token 时拒绝，并指向控制台。401/403 时让用户在 Plugins 设置中更新
  token（或更新启动环境）后重启 Harness，不要用猜测的 token 重试。

## 典型流程

点餐：

1. 查门店/菜单（只读）
2. 选商品，确认库存/可售状态（只读）
3. `calculate-price` 算价（只读）
4. 按“金额单位”规则展示明细，询问确认
5. 用户明确确认后调用 `create-order`
6. 返回订单号、取餐信息；如需支付，严格按工具返回的指引操作，不编造支付链接

优惠券：

1. 查可用券/领券（只读）
2. 说明绑定或抵扣对价格的影响
3. 用户明确确认后调用 `auto-bind-coupons`（或服务端对应的券工具）
4. 重新算价并向用户复核

## 输出与错误

- 金额、时间、地址、订单号必须忠实转述工具结果；工具没返回的信息不要编造。
- 业务错误要说明关键 code/message 和下一步；不要吞掉错误后说“已完成”。
- 下单成功回报订单号；失败要说明是否可能已创建（先查订单再决定是否重试）。
- 用中文回答时保留工具原始错误码，便于排查。

## 禁止事项

- 硬编码工具清单、数量或参数 schema。
- 未经用户明确确认调用 `create-order`、`auto-bind-coupons` 等写工具。
- 混淆分/元、静默换算、或把未知单位当成元。
- 高频并发、无限重试、绕过 429 退避。
- 在任何输出中暴露 `MCD_MCP_TOKEN`，或把它写进插件源码、仓库或回答。
